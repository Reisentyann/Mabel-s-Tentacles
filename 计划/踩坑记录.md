# 踩坑记录

> 记录开发过程中踩过的坑和根因，避免重复踩。每一条都写清楚「现象 → 根因 → 正确做法」。

## 1. 相对路径 vs 进程工作目录（CWD）

**现象**：本地跑后端，`/api/files/` 返回空，但项目根 `data/` 里明明有文件。

**根因**：
- 配置里 `data_dir: "./data"` 是**相对路径**，它相对的是**进程的工作目录（CWD）**解析，不是相对 config.yml 所在目录，也不是相对 exe 所在目录。
- `start-dev.ps1` 用 `Start-Process -WorkingDirectory mcp-server-go` 启动后端，所以后端 CWD = `mcp-server-go`，`./data` → `mcp-server-go/data`（空）。
- Docker 里 CWD 是 `/app`（且 `./data` 挂载到根 `data/`），所以同一句 `./data` 在 Docker 里碰巧正确。**一份配置、两种 CWD、解析出两个不同绝对路径**。

**正确做法**：
- 路径一律用**绝对路径**，或明确「相对项目根」的语义，再由启动脚本解析成绝对路径。
- 本项目方案：`.env` 里写「相对项目根」的路径（`DATA_DIR=data`、`LOG_FILE=logs/server.log`），`start-dev.ps1` 里用 `Join-Path $Root $val` 解析成绝对路径再传给后端（`$Root = $PSScriptRoot`）。

## 2. .env 凭据与运行中容器凭据不一致

**现象**：后端连库报 `password authentication failed for user "agent_user"`。

**根因**：
- `.env` 里 `POSTGRES_USER=agent_user`，但运行中的 `agent_postgres` 容器是早期用默认值 `postgres/postgres` 创建的。
- Postgres 容器的 `POSTGRES_USER/PASSWORD` 只在**首次初始化（空卷）**时生效，改 `.env` 不会影响已存在的容器，除非重建。

**正确做法**：
- 改 `.env` 前先确认运行中容器的真实凭据：`docker inspect <容器> --format '{{range .Config.Env}}{{println .}}{{end}}'`。
- 要改凭据就得重建容器（注意数据卷）。

## 3. 连库无超时 → 无限挂起

**现象**：双击 `bin/server.exe`，控制台空白、像卡死，无任何输出。

**根因**：
- 默认数据库 host 是 `postgres`（Docker 内网域名），Windows 上解析不了。
- 连库代码没有超时，`pool.Ping` 卡在 DNS 解析/连接上，而「database connected」或「connect database failed」的日志在 Ping 之后，所以**全程无输出**。

**正确做法**：
- `pgx` 连接必须设超时：`cfg.ConnConfig.ConnectTimeout` + `pool.Ping` 用带超时的 context。
- 连接失败要在日志里给出可操作提示（如「set DATABASE_URL env ...」）。

## 4. 后台进程日志被重定向到文件 → 控制台看不到

**现象**：跑 `start-dev.ps1`，后端看起来「没有输出」。

**根因**：
- 脚本用 `Start-Process -RedirectStandardOutput <文件>` 启动后端，日志全进了文件，控制台看不到。
- 后端本身只写 `os.Stdout`，一旦 stdout 被重定向，控制台就空了。

**正确做法**：
- 后端日志要**同时**写控制台和文件：`io.MultiWriter(os.Stdout, 日志文件)`（见 `internal/logging/logging.go`）。
- 本地启动时后端在独立控制台窗口输出（`Start-Process` 不加重定向），文件由后端自己写。

## 5. 编码约定：SQL 必须用参数化查询，禁止拼接用户输入

**规则**：所有 SQL 一律用 `$1/$2/...` 占位符传参；**禁止**用 `fmt.Sprintf` / `+` 把用户输入拼进 SQL 字符串。

**为什么**：手写 SQL（pgx）防注入靠的是「参数与 SQL 分开发送」——用户数据走 `$n` 占位符，永远不会被当成 SQL 代码解析。

**允许的例外**：拼接**硬编码常量**（如列名列表 `commandColumns`、`metaColumns`、`metaWhere`），不含任何用户输入，是安全且推荐的做法（避免重复写列名）。

**自查清单**（写新查询时）：
1. 用户输入是否全部走 `$n` 占位符？
2. 有没有 `fmt.Sprintf("...%s...", 用户输入)` 进 SQL？
3. 列名/表名是否来自用户？（若来自用户，必须白名单校验，不能直接拼）
