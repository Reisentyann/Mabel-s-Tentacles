# 文件描述系统测试规则

> 本规则定义文件描述系统（describer-go + LLMStore + 元数据落库）的测试过程。
> 测试素材由 skill `build-test-fixtures` 构造（见 `.opencode/skill/build-test-fixtures/`），
> 字段语义以 `docs/元数据字段说明.md` 为唯一权威。

## 1. 分层

| 层 | 测什么 | 依赖 | 状态 |
|---|---|---|---|
| L1 单元/集成 | 插件算法、闸门策略、合并语义、确定性 | 无 DB，`go test` | 已常态化 |
| L2 夹具端到端 | 真实形态文件 → 全插件流水线 → 字段断言 | 无 DB，verify 工具 | 本规则主战场 |
| L3 中间件安全 | LLM 违规写操作 → 拒绝与墓碑 | L1 已覆盖，部署后实测 | 已常态化 + 手工 |
| L4 部署链路 | write_file/describe_file 经 DB 落库 | postgres + 服务 | 待 T3 analyze 端点后自动化 |

## 2. 环境

- L1/L2 只需要 Go 1.26+，无需数据库
- L4 需要 `docker compose up -d postgres` 后 `./start-dev.ps1`（或线上环境）

## 3. L1 命令（每次改 describer-go 必跑）

```powershell
Set-Location describer-go; go test ./...
Set-Location ..\mcp-server-go; go test ./internal/...
```

全部 `ok` 才算过。确定性测试（同一输入两次分析逐字节相等）失败 = 插件引入了非确定因素，禁止放过。

## 4. L2 夹具测试（核心流程）

夹具目录：`test/fixtures/`（清单见 `test/fixtures/清单.md`）。

### 步骤

1. （可选）用 skill `build-test-fixtures` 补充/更新夹具，并登记清单
2. 生成图像夹具：仓库根执行 `go run ./test/tools/gen_png.go`
3. 跑验证器输出全量字段报告：

```powershell
Set-Location describer-go
go run ./cmd/verify ../test/fixtures ../test/fixtures-report.json
```

（verify 不传 ExtMime，报告不含 `cod-basic-mime-match`——该字段只在 DB 写入链路产出。）

4. 按下方**断言表**核对报告（模型核对或人工核对皆可）；任何"必现字段缺失"或"必失字段出现"即失败
5. 报告文件 `test/fixtures-report.json` 不入库（已在 .gitignore，属运行产物）

### 断言表（✅=必现，🚫=必须不存在；P0/P1 标注 = 候选字段实现后启用）

| 夹具 | 断言 |
|---|---|
| `小说/深夜书架.txt` | ✅ `cod-text-language=zh`、`cod-text-headings` 含第一/二/三章、`cod-text-structure` 含 headings、`cod-text-cjk-ratio>0.5`；P0: paragraphs>0、dialog-ratio>0、avg-para-len>30。🚫 `cod-image-*`、`cod-code-*` |
| `攻略/狼人杀新手攻略.md` | ✅ `cod-text-structure` 含 headings+lists+tables、`cod-text-title-line` 非空；P0: table-rows>0、list-items>5。🚫 `cod-image-*` |
| `日志/server.log` | ✅ `cod-text-encoding=utf-8`、`cod-text-blank-ratio<0.1`（无空行；末尾换行产生的空行不算异常）、无 `cod-text-headings` 键（缺失即未分析）；P0: timestamp-count>0、repeat-line-ratio>0.2、line-len-std<5、digit-ratio>0.1 |
| `数据/players.csv` | ✅ `cod-basic-textish=true`；P1: `cod-csv-cols=3`、`cod-csv-cols-consistent=true`；`players-broken.csv` 为 `cols-consistent=false` |
| `配置/app.json` | ✅ `cod-text-encoding=utf-8`；P1: `cod-json-top-keys>0` |

| `聊天/群聊记录.txt` | ✅ `cod-text-cjk-ratio>0.3`；P0: mention-count>0、emoji-count>0、avg-line-len<40 |

| `编码/crlf-note.txt` | ✅ `cod-text-encoding=utf-8`；P0: `cod-text-eol=crlf` |

| `图像/ai-gen.png` | ✅ `sp-cod-png-prompt` 存在且非空、`sp-cod-png-parameters` 存在 |

### 失败处理

- 字段缺失：先查插件 `Supports` 路由（basic 事实是否正确产出），再查插件本身
- 字段值错：对照字段字典第 4 节的算法描述逐项排查；修完必须回归 L1
- 出现"必失"字段：路由串味，属严重缺陷，立即修

## 5. L3 中间件安全用例

单元层已由 `describer-go/llmstore_test.go` 常态覆盖。部署后按此表用 `describe_file` 实测：

| 输入 attributes | 预期 |
|---|---|
| `{"cod-image-width": 999}` | rejected，原因含"cod 区只读" |
| `{"sp-cod-png-prompt": "篡改"}` | rejected（sp-cod 同属只读区） |
| `{"llm-source": "ollama:spoof"}` | rejected（审计字段系统专属） |
| `{"llm-semantic-type": "科幻小说"}` | rejected（词表外） |
| `{"sp-llm-游戏名": null}` | 既有 `sp-llm-游戏名` 被删除（null 墓碑） |
| `{"sp-llm-新观察": "任意"}` | 通过 |
| 不传 attributes | `llm-at` 不变（空操作不盖戳） |

## 6. L4 部署链路（当前形态）

现状：夹具进入 `data/` 的唯一自动触发是 MCP `write_file`（RecordFileMeta 全流水线）。
步骤：起服务 → 用 MCP 客户端（AstrBot 或测试客户端）`write_file` 写入夹具内容 → SQL 核对：

```sql
SELECT attributes FROM file_metadata WHERE file_path = '<写入路径>';
```

核对点：cod 字段与 L2 报告一致；`cod-basic-mtime` 为写入时刻；再调 `describe_file` 传 llm 字段 → 核对 `llm-*` 与 `llm-source=agent` 共存。
**待 T3（HTTP analyze 端点）实现后**，此层改为脚本化：直接 POST 文件路径触发分析。

## 7. 回归触发清单

| 改了什么 | 必跑 |
|---|---|
| 任何 describer-go 代码 | L1 + L2 |
| 新增/修改字段（含 P0/P1 落地） | L1 + L2 + 字段字典变更记录 + 断言表更新 |
| LLMStore 策略 | L1 + L3 |
| RecordFileMeta / describe_file / HTTP describe | mcp-server-go 测试 + L4 |
| Dockerfile / compose / go.mod replace | `docker compose build backend` 必须成功（构建上下文=仓库根） |

## 8. 夹具扩充流程

1. 触发 skill `build-test-fixtures`（"构造测试文件/生成夹具"），声明新夹具类型与要测的字段
2. skill 按配方生成到 `test/fixtures/<类>/`，登记 `test/fixtures/清单.md`
3. 在本规则断言表追加一行（✅/🚫/P0/P1 标注）
4. 跑 L2 全量核对
