# 架构设计（组件职责与约定）

> 本文档记录组件级设计决策：每个组件知道什么、不知道什么、组件间怎么流转。
> 字段定义见 `元数据字段说明.md`，测试见 `test/测试规则.md`——本文只管"架构形状"。
> 状态：describer / repo / 索引机（indexer-go 模块级）为已实现现状；管理机为规划定稿（2026-09-03）。

## 1. 组件总图（知识的单向集中）

| 组件 | 知道 | 不知道 | 一句话定位 |
|---|---|---|---|
| describer-go | 内容→事实的确定性算法 | 文件在哪、彼此关系 | 字节进、事实出（纯库，零 IO 零 DB） |
| 索引机 indexer | 字段值 → uuid 的映射 | 文件在哪、内容是什么 | 纯查询：条件 → uuid 集合 |
| 管理机 manager | **文件在哪（位置）、文件关系（谱系）** | ——（它的领地） | 唯一知情者，其他组件都来问 |
| repo | SQL 与表结构 | 业务规则 | 数据怎么存（可 mock） |
| DB | 事实源（元数据/uuid/向量） | —— | 索引兜底 + pgvector 语义检索 |

核心原则：**组件不越过管理机摸文件系统，不越过 repo 摸 SQL，不越过 describer 造字段。**
跨层问题路由到对应组件，加新组件不需要了解文件系统结构，只需要管理机的接口。

**仓库布局（模块平级，Go std 范式，与 describer-go 同款接线——mcp-server-go 经 replace 引用，
Docker 构建上下文 = 仓库根）：**

```
Mabel-s-Tentacles/
├── mcp-server-go/   装配层：HTTP + MCP + 薄壳，组合下列模块
├── describer-go/    描述引擎（纯库，零 IO 零 DB）
├── indexer-go/      索引机（纯库，零依赖 sink）
└── manager-go/      管理机（依赖倒置：Store 最小面注入，不 import 兄弟模块）
```

## 2. 组件间货币与依赖方向

- **货币是 uuid**：索引机产出 uuid 集合 → 管理机凭 uuid 取件（repo 补按 uuid 批量接口）→
  agent / HTTP 拿到的是管理机给的业务视角
- **依赖单向**：`HTTP / MCP 工具层 → manager → repo + describer + indexer`
- **indexer 是 sink**：谁都能调它，它零出调用（不调 repo、不调 manager、不通知任何人）
- **返回值是数据不是回调**：`[]uuid` / `[]FileRef` 切片就地返回，链的每一步在调用者栈里结束，
  不会滚成环（链式调用问题的结构性解法）

## 3. 索引机（已实现，2026-09-03）

**形态**：独立 Go 模块 `indexer-go/`（与 describer-go 同级，纯库零依赖）；
启动时从 DB 全量 Rebuild（个人库量级秒级）；
现有 SQL 检索（`search/sql.go`）保留为兜底路径，索引故障系统照常能搜。

**实现要点**（bucket.go 三型桶 + mem.go 内存实现，均已带测试）：

- 桶型由字段首个可索引值自动决定（数值→num / 标量→enum / 数组→multi），
  加字段=加桶零配置；挂载与查询两侧共用归一化原语（int/float64/数字字符串同形）
- RWMutex：Query 读锁 / Update·Rebuild 写锁，进程内并发安全
- 脏值 best-effort：nil / 对象 / 纯对象数组（如 palette）静默跳过——
  DB 是事实源，不值得为脏值中断喂食
- Update 幂等：桶级 add/remove 幂等 + "值没动不碰桶"；new 为空 = 整体移除（删除路径）
- 结果升序返回（map 迭代序随机，排序保证确定）

**数据结构（每字段独立桶，加字段=加桶，不动别的桶）**：

| 字段类型 | 桶结构 | 查询 |
|---|---|---|
| 枚举 / bool | `map[值] → uuid 集合` | 等值 O(1) |
| 数值 | `(值, uuid)` 有序切片 | 二分范围 |
| 数组（llm-characters / tags） | 值 → 集合，多值挂载 | 等值 |

**接口**：`Query(conds, and/or) []uuid` / `Update(ref, old, new)` / `Rebuild(all)`。

**喂食点（写路径全部收口）**：T1（`RecordFileMeta`）/ `describe_file` / T2 回填，
Upsert 后由编排方调 `Update` 做 diff 增量（旧桶移除、新桶挂入）。
**绕口兜底**：`execute_command` 直改文件绕过一切写路径——盘变了 DB 没变，索引自然没变；
靠 IsStale 条件 3（checksum 漂移）对账发现 → 重分析 → Upsert → 索引随之更新（最终一致）。

**为什么不是 PG 索引**：检索逻辑演进（中文分词全文 / BM25 评分 / 聚合 facets）在 SQL 里
受限且难维护；纯 Go 包内演进自由。
**为什么不是独立服务（ES 形态）**：双写同步链 + 一致性窗口 + 运维成本；
进程内 + 可重建 + 接口隔离，将来多实例再外部化，调用方不改。
**向量检索例外**：pgvector + hnsw 留在 DB（llm 轨语义搜索将来直接用），不归索引机。

## 4. 管理机（规划定稿）

**定义**：文件位置与谱系的**唯一知情者**。其他组件不需要知道文件在哪、
不需要知道文件之间的关系——只需要问管理机。

**形态**：独立 Go 模块 `manager-go/`（与 describer-go 同级）。依赖倒置——自定义
`Store` 最小面接口（io.Reader 模式），mcp-server-go 的 repo 实现满足签名后注入，
manager 不 import 任何兄弟模块；updater 将来 require describer-go 与 indexer-go（同级 replace）。

**模块**：

| 模块 | 职责 |
|---|---|
| placement | 路径校验；move = 物理改名 + 元数据迁移 + 谱系边（MCP `move_file`） |
| download | 短期票据 URL（签名 + 过期），HTTP handler 只验签不出链接；download_count 归它 |
| updater | T2 启动回填（IsStale→Analyze→Merge→Upsert）+ T3 analyze 入口；连续 3 轮盘上缺失 → SoftDelete |
| audit | 盘 vs DB 对账（孤儿文件 / 幽灵元数据 / 重复 checksum）→ 报告给 agent，**不自动动手** |

**铁律**：
1. DB 交互归 repo——manager **编排** repo（调用），不**拥有**它（不写 SQL）；
   describer 保持纯库不碰 DB
2. 自动只巡检报告，动手必须显式（`move_file`）——路径是 agent 的组织语言 + 元数据唯一键，
   后台自动归档会破坏 agent 路径预期
3. 编排循环发生在**时间轮次**（timer / 启动驱动），不发生在调用栈里——
   一轮 = 查→处理→写→结束，绝不自旋，无递归无栈累积

**挂进来的存量待办**：T2 / T3 / 软删除（`SoftDeleteMetadata` 闲置中）/ 文件谱系图（lineage 表）。

## 5. 工程规范

- **日志字段五要素**：入口 / `session`·`user` / 操作现场 / `duration` / 结果
  （失败必带 `error`，成功带产出计量）——权威定义见 `mcp-server-go/internal/logging/logging.go` 包注释
- **文件标识头**：每个 .go 文件顶部两行（路径+用途 / 修改日期），
  日期由 `fresh-header.ps1 -Changed` 刷新，勿手改
- **改完代码收尾**：刷头 → gofmt → 双侧 `go test`
  （完整清单见本地 skill `code-modify-rules`）

## 6. 决策记录（为什么是现在这个形状）

| 日期 | 决策 | 动因 |
|---|---|---|
| 2026-09-03 | 字段量化器 → 取消，改为索引机 | agent 读字段字典就会拼条件，量化聚合增值有限；离散字段的真实痛点是检索 |
| 2026-09-03 | 索引机不放 PG（GIN 形态否决） | 检索能力焊死在 SQL：中文全文/评分/聚合演进受限 |
| 2026-09-03 | 索引机不做独立服务 | 双写同步链 + 一致性窗口；进程内 + 可重建 + 接口隔离足够 |
| 2026-09-03 | 索引机 = 条件→uuid 纯查询，uuid 是组件间货币 | 职责单一；数据面最小；组合自由 |
| 2026-09-03 | 管理机 = 位置与谱系唯一知情者 | 知识单向集中；调用链收敛；移动/谱系/软删除天然归它 |
| 2026-09-03 | 链式调用三铁律（sink / 返回数据 / 写不自旋） | 组件协作不滚成环的结构性保证 |

## 7. 架构评审记录（2026-09-04）

评审人：外部架构视角。结论：**三机架构（describer/indexer/manager）整体合理，维持现状**。
知识单向集中、依赖单向、uuid 货币、sink 铁律、返回数据不回调——结构性决策均正确，
个人库量级下无过度设计。发现 4 个问题，处置如下：

| # | 问题 | 严重度 | 处置 |
|---|---|---|---|
| 1 | 5MB/512B 预算截断职责旁落调用方：describer.go 注释把截断写成 Loader 职责，但 T1（RecordFileMeta）直传全量 content，超大文本会让 text 插件全量解码切 rune（内存数倍膨胀），字段字典"全读 5MB"承诺与实现不符 | 真实缺陷 | **已修**：截断下沉 Analyze 入口（`MaxHeadBytes`/`MaxFullBytes` 常量），纯字节切片不违反零 IO 铁律，调用方从此不可能漏 |
| 2 | 索引机无自省接口：排查"索引与 DB 不一致"时无抓手 | 运维缺口 | **已修**：`Stats()`（fields/keys/mounts），成本极低 |
| 3 | 桶型由"首个可索引值"推断：字段类型漂移时行为依赖挂载顺序 | 理论风险 | **不改**：字段类型受字段字典约束实际稳定；若将来漂移，Rebuild 即自愈（启动全量重建）。记录为已知取舍 |
| 4 | 查询能力缺口：单层 And/Or、字符串无子串匹配（现走 SQL LIKE 兜底） | 演进方向 | **记录**：trigram 桶是语言无关全文的演进方向（中文 2-gram 同构），需要时再加，调用方接口不变 |

同批落地：P2 字段扩张 35 个（describer 四家族版本各 +1，字段字典 4.1-4.4 与 4.8 候选区）。
