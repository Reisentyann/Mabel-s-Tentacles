## 1. 架构与需求背景（30 秒版）

- 项目三机：描述机（describer-go，字节进→90+ 量化字段落 PostgreSQL 的 file_metadata.attributes JSONB）/ **索引机（indexer-go，字段条件→uuid，纯内存桶）** / 管理机（manager-go，uuid→物理位置）。编排机（mcp-server-go/core）串联，DB 是事实源，索引是派生缓存（启动 RebuildIndex 全量重建 + 写路径 Sink.Update 增量喂食 + SQL 兜底降级）。
- 需求：外部 agent 要能查文件 → 两次调用封顶的设计：**`list_index_fields`（字段目录发现，一次拿全部可查字段+桶型+取值/值域，可缓存）→ `search_files`（条件查询 `[{"field","op","value"}]`，op 全量 eq/in/gt/lt/range，多条件 And）→ read_file 取内容**。
- 查询链路：工具/HTTP → 编排机 `SearchByConditions`（索引优先；eq/in 出错可折回 SQL 降级；gt/lt/range 是索引专长不降级宁缺毋滥）→ uuid 批量取件 → 观察者复判（非 admin 只见 public/自己/本组）→ updated_at DESC 分页。

## 4. 「怪病档案」结案（2026-09-10，必读——这是本仓永久性陷阱）

**真相：从来没有什么文件系统怪病。** 昨天卡死的 `no required module provides package` 错误，
真因是两处 import 路径**少写了一个 n**：

| 位置 | 错误写法（1 个 n） | 正确写法（2 个 n，= go.mod 的真名） |
|---|---|---|
| all.go 第 18 行（readfile blank import） | `github.com/Reisentyan/...` | `github.com/Reisentyann/...` |
| listindexfields.go 第 24 行（common import） | `github.com/Reisentyan/...` | `github.com/Reisentyann/...` |

**为什么这个 typo 能伪装成怪病**（都实测复盘过）：

- 1-n 路径不匹配任何模块 → go 在模块图查无此名就报错，**连磁盘都不碰**
  （ProcMon 追踪实锤：common 目录零文件系统访问），所以看着像「文件被搞坏/驱动拦截」
- 错误信息里的路径和正确路径只差一个字符，肉眼极难分辨（`Reisentyan` vs `Reisentyann`）
- git index 里的内容本身就带 typo → `git checkout` 重写多少次都一样失败
- 好窗口/坏窗口的「随机性」是测试时手敲路径偶对偶错的巧合，不是系统状态
- 用户名是 `Reisentyan`（1 个 n），module 路径是 `Reisentyann`（2 个 n）——**这个陷阱永久存在**

**给未来会话的排障铁律**：遇到 `no required module provides package X`，第一件事把错误信息里的
X 与 go.mod 的 module/require 行**逐字符比对**（或直接 `grep -n 'Reisentyan/'`——1-n 后跟斜杠
只可能命中 typo）。排除 typo 之前，禁止怀疑杀软/驱动/文件系统。昨天的「已排除清单」（工具链/缓存/
go.work/vendor/8.3 短名……）全部白做，就是在 typo 上绕的弯路。误诊期间还冤枉了完美世界对战平台的
反作弊驱动（MessageTransfer.sys，已被用户卸载）——它是清白的。

诊断过程留下的证据文件（处置归人类）：`旧内容/` 里有大量实验残留（重试归档/探针目录等）；
ProcMon 与 trace 文件在系统临时目录，不影响仓库。
