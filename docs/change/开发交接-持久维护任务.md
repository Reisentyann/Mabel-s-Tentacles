## 一、背景与目标

**问题**：write_file / copy_file / jm_comic 导入 / 目录写入 / HTTP 复制这些路径，  
在管理机 Write/ImportFile 成功后只调 `orch.Submit()`——进程在此之后崩溃，  
维护通知丢失，索引不更新。

**目标**：
- **A**：在 Submit 之前先调 `PrepareMaintenance` 把意图落库；进程重启后由 `RetryMaintenance` 接手。
- **B**：管理机 T2（Backfill）/ T3（AnalyzeFile）的 DB 读改写绕过了编排机 `updateMu`，  
  可能与编排机的 execute/processMaintenance 并发写同一行属性——需纳入串行锁。

### 插入模式（每处一样）

```go
if ms, ok := deps.Store.(repo.MaintenanceStore); ok {
    if _, perr := ms.PrepareMaintenance(ctx, receipt.UUID, "write"/*或"copy"*/, sessionID, actorName); perr != nil {
        slog.Warn("xxx prepare maintenance failed", "uuid", receipt.UUID, "error", perr)
```

## 三、B 未完成（下次接着做）

### 问题

`manager-go/updater.go` 的 `analyze()`（T3）和 `Backfill`（T2）直接读改写 DB 并调 `m.sink.Update()`，  
绕过了编排机的 `updateMu`。

- `m.sink` 是 `managerIndexSink`，其 `Update` 内部会取 `updateMu`——索引发布已串行 ✓  
- 但 DB 的 `UpsertMeta`（T3：`updater.go:214`）和 `SoftDeleteMeta`（T2：`updater.go:116`）仍在锁外 ✗

### 原方案已撤销：必须避免重复加锁

以下旧方案代码仅保留作为问题记录，不能作为实施模板：外层持 `updateMu` 调用 `mgr.AnalyzeFile` 或 `mgr.Backfill`，管理机内部再调用 `managerIndexSink.Update`，后者也持同一个非重入 `sync.Mutex`，会死锁。`runMaintenance` 包裹管理机分析同样存在此问题，且不能传空 UUID 准备任务。

推荐下一步：设计管理机逐文件读改写的注入式串行执行钩子，明确锁内索引发布由谁负责；在同一临界区重读元数据、合并、提交并发布索引，索引回调不能再次取同一把锁。分析耗时与锁粒度应通过测量确认。

需要覆盖 HTTP、MCP `analyze_file`、启动后台 Backfill 的全部调用入口，仅改 HTTP 两行不完整。补充并发属性保留测试与完成超时测试，验证既无覆盖也无死锁。

### 旧方案记录（不可直接执行）

**Step 1**：在 `core/orchestrator.go` 加方法（`updateMu` 已是 `sync.Mutex`）：

```go
// RunWithUpdateLock 在编排机串行锁内执行 f（T2/T3 的 DB 写路径专用）。
func (o *Orchestrator) RunWithUpdateLock(f func()) {
    o.updateMu.Lock()
    defer o.updateMu.Unlock()
    f()
}
```

**Step 2**：在 `core/maintenance.go` 加两个门面（参考 `ModifyFile` / `MoveFile` 的模式）：

```go
// AnalyzeFile T3 门面：持 updateMu 后调 mgr.AnalyzeFile。
func (o *Orchestrator) AnalyzeFile(ctx context.Context, mgr *manager.Manager, path string) (*manager.AnalyzeReport, error) {
    var report *manager.AnalyzeReport
    err := o.runMaintenance(ctx, "" /*uuid 由内部读取*/, Event{Kind: KindAnalyze, Path: path}, func() error {
        var e error
        report, e = mgr.AnalyzeFile(ctx, path)
        return e
    })
    return report, err
}
```

> 注意：`runMaintenance` 已持 `updateMu`；但它需要 uuid，T3 先 `GetMetadata` 拿 uuid 再进锁——  
> 更简单的做法：直接在门面里 `o.updateMu.Lock()` 包住 `mgr.AnalyzeFile` 调用，不走 `runMaintenance`。

**最简实现**：

```go
func (o *Orchestrator) AnalyzeFile(ctx context.Context, mgr *manager.Manager, path string) (*manager.AnalyzeReport, error) {
    o.updateMu.Lock()
    defer o.updateMu.Unlock()
    return mgr.AnalyzeFile(ctx, path)
}

func (o *Orchestrator) Backfill(ctx context.Context, mgr *manager.Manager, batch int) (int, error) {
    o.updateMu.Lock()
    defer o.updateMu.Unlock()
    return mgr.Backfill(ctx, batch)
}
```

**Step 3**：`mcp-server-go/internal/api/analyze.go` 的两处调用改用编排机门面：

```go
// analyze.go:56 原来：
report, err := s.manager.AnalyzeFile(r.Context(), req.Path)
// 改为：
report, err := s.orch.AnalyzeFile(r.Context(), s.manager, req.Path)

// analyze.go:79 原来：

// 改为：

```

> `s.orch` 在 `api/router.go:Server` 结构里已有；`s.manager` 也有。不用改 Server 结构。

**注意**：ctx 取消不能中断 `sync.Mutex.Lock()` 的等待。不能用“支持 ctx”证明上述旧方案不会卡住。

## 建议

本节为历史建议。B 不能通过简单外层加锁完成；`AnalyzeSingleRow` 是伪代码，不是现有 API；tools 还需要授权与元数据读取能力，不能直接把完整 Store 换成只有两个写方法的接口。扩展建议以 [架构评价与建议](../架构评价与建议.md) 的维护修正为准。

### 必须做（影响正确性）

**1. B 任务先于推送** updateMu 锁外的 UpsertMeta 是真实并发风险。虽然概率低，但索引与 DB 不一致时，表现是搜到的文件内容和实际不符——这种 bug 在生产里极难定位。B 任务的代码量不大（orchestrator.go 加一个方法，analyze.go 改两行调用），值得在推送前做完。

**2. maintenance_test.go 的 PostgreSQL 验证** 状态约束的 ALTER TABLE 在 PG 不同版本上行为有差异。这个测试目前"最后一次修正后没有重跑"——在推送前用真实 PG 跑一次是必要的，不是可选的。

### 应该做（影响健壮性）

**3. Backfill 逐文件持锁，而不是整轮持锁**

当前 B 任务的最简实现是 `o.updateMu.Lock()` 包住整个 `mgr.Backfill` 调用。Backfill 扫全表，batch=100 时持锁时间可能是几秒到几十秒，这段时间内编排机的所有 worker 都在排队。

更好的改法：在 `core` 包加一个 `BackfillWithLock` 门面，在循环内逐文件持锁：

```go
// 伪码
for each row in pages {
    o.updateMu.Lock()
    mgr.AnalyzeSingleRow(ctx, row)
    o.updateMu.Unlock()
}
```

这样锁粒度细，worker 可以在文件分析间隙插入执行。当前简单实现够用，但 batch 大时会有感知延迟。

**4. 给 tools 层收窄 Store 接口**

新建一个 `tools.StoreWriter` 接口，只暴露工具层真正需要的方法：

```go
type StoreWriter interface {
    RecordOperation(...)
    PrepareMaintenance(...)
}
```

`Deps.Store` 换成这个接口。不急，但这能防止工具层日后悄悄增加 DB 调用，边界会更清晰。

### 值得考虑（影响可观测性）

**5. 维护任务的监控端点**

`RetryMaintenance` 现在是定时触发的内部调用，但没有暴露给外部的观测面。建议加一个 HTTP 端点：

```text
GET /api/admin/maintenance/stats
```

返回 `prepared/ready/retry/done` 各状态的任务数。这样当进程崩溃重启后，能立刻看到有多少待处理任务，而不是等日志里出现 Warn 才发现。实现简单，一条聚合 SQL 就够。

**6. `managerIndexSink.Update` 读 DB 失败时的降级日志加 uuid**

当前改动（`maintenance.go` 的 Warn 那条）已经记了 uuid 和 error，这很好。确认 Warn 里包含足够上下文（uuid、old/new 的 key 数）——索引不一致问题靠这条日志定位。

### 长期方向（不急，但值得想）

**7. describer-go 家族的版本升级策略**

`IsStale` 四条件能检测到"引擎升级了但这个文件还没重分析"，Backfill 会补跑。但如果某次引擎升级影响了大量文件，Backfill 可能要跑很久。可以考虑给 Backfill 加一个"仅重分析特定家族"的参数，这样升级 text 家族时不用全量重跑 image 家族。

**8. 多进程扩展的边界**

当前 `updateMu` 是进程内锁，`PendingMaintenance` 用 `FOR UPDATE SKIP LOCKED` 做分布式互斥，两者是不同层级的保护。目前单进程单实例，没有问题。如果将来想跑多实例，`updateMu` 需要换成 DB 级别的 advisory lock 或者 per-uuid 行锁——这是一次较大的改动，提前知道边界在哪就好，不用现在动。

### 一句话总结

短期：先把 B 任务和 PG 验证做完再推。中期：Backfill 细粒度锁 + 维护任务监控端点。长期：tools 层接口收窄、多进程扩展路径保持清醒。整体方向是对的，继续做。
