# Mabel-s-Tentacles 架构评价与建议

> 评价时间：2026-10-10  
> 来源：开发会话中的架构评价；此前模型署名不准确，本文不据此归属模型。

## 维护修正（2026-10-10）

本文是评审意见，不是已验证的架构规范。以下修正优先于后文历史评价：

- 简单持 `updateMu` 调管理机 AnalyzeFile/Backfill 会与 `managerIndexSink.Update` 重复加锁并死锁。应明确逐文件读改写与索引发布的锁所有权，覆盖 HTTP、MCP、后台回填三类入口。
- A 仅完成代码编辑。`prepared` 不在 PendingMaintenance 的常规领取范围内，只有启动恢复才转为 ready；异步 Submit 成功后也未关联任务完成。需要设计 ready/done 流转，避免任务长期滞留。
- RetryMaintenance 当前以 KindAnalyze 重建；它不等价于带 AgentMeta/Visibility 的原始写事件。恢复时是否保留归属、可见性、JM 来源字段需要专项验证。
- Write 成功后再插入意图仍有崩溃窗口，插入失败仅 Warn 也无法保证持久性。“完全崩溃安全”需要更强的入库事务或 outbox 设计。
- tools 还需要授权、元数据读取等方法，不能直接用只含 RecordOperation/PrepareMaintenance 的接口替换 Deps.Store；应按实际用途收窄。
- UUID 物理路径是布局解耦，不代替授权校验。MCP 与 HTTP 同为协议入口，共享业务门面才能减少逻辑重复。
- DB 往返延迟、Backfill 持锁时长、全量索引重建与大结果集查询成本尚未测量，不宜给出固定毫秒数或效率结论。

## 建议优先级

1. 正确性：完成维护任务状态流转、恢复字段语义、无死锁的串行更新与真实 PostgreSQL 迁移验证。
2. 可观测性：暴露任务状态计数、最老待办年龄、重试耗尽数，记录分析耗时与队列积压。
3. 性能：测量写入、检索、回填和重建，再决定是否采用逐 UUID 锁或分家族重分析。
4. 边界：让 HTTP/MCP 共享维护门面，按使用方收窄存储接口；多实例部署需另行设计 DB 并发保护。

当前实施状态见 [持久维护任务交接](change/开发交接-持久维护任务.md)。

## 一、总体判断

**有想法，且想法是对的；执行上有几处值得注意的张力。**

这不是一个普通的文件管理项目。大多数同类项目是 S3 包装器，这个的独特之处在于三点：

1. **描述智能内嵌进了文件生命周期**——describer-go 的多家族分析管线让文件一进来就自动产出结构化事实，不靠人工打标
2. **MCP 作为控制面而不是 REST**——agent 直接参与文件管理，少一层中间人
3. **物理随机化 + 逻辑键分离**——安全模型（visibility/owner）和存储布局完全解耦，在"个人网盘 + 多用户共享"场景下比路径权限控制干净得多

## 二、值得肯定的地方

**三机分离，职责清晰**

describer-go（字节进事实出）/ indexer-go（条件→uuid）/ manager-go（位置与谱系）各司其职，边界是接口而不是包引用。这个切法在同体量项目里不常见，说明有意识地在控制耦合。

**intake 域的物理随机化**

逻辑键与物理路径解耦，agent 只见逻辑键，盘面不可猜。Move 因此变成纯 DB 键改、内容不动；软删除不产生孤立文件。注释里写清楚了原因，后人能看懂。

**容灾三铁律是显式的**

"源文件不能丢 / 描述可丢可重建 / 降级不阻塞"写进了包注释，不是隐含假设。维护者改动时知道什么不可违反。

**事件队列 + worker 的异步模型**

写路径盘写成功即返回，描述/落库/喂索引异步跑。对 MCP 对话交互场景是正确选择。

## 三、需要注意的张力

**1. updateMu 是当前最大隐患**

`managerIndexSink.Update` 已持锁，但 `manager-go/updater.go` 里的 `UpsertMeta`（T3）和 `SoftDeleteMeta`（T2）在锁外。T2/T3 和编排机 worker 可以同时写同一行 attributes，后写覆盖先写。单机单进程场景概率不高，但出了极难复现。B 任务方向正确，但 Backfill 持锁时间可能较长，会让 worker 完全停摆。

**2. PrepareMaintenance 的幂等代价**

写入成功后落 `prepared`，重启后 RetryMaintenance 会再跑一次 executeUnlocked。execute 是幂等的（MergeResults 整族替换），重复跑结果恒等，代价可接受——但如果将来 execute 有副作用（如发通知），需要重新审视。

**3. manager-go 是准模块但有潜在循环依赖风险**

manager-go 不知道 mcp-server-go，目前单向依赖没问题。但如果将来 manager-go 需要直接调用 MaintenanceStore，就会形成循环。注意不要往这个方向演进。

**4. tools 层持有完整 repo.Store 有轻微越权**

MCP 工具层理论上可以调任何 DB 方法。长期来看，给工具层暴露更小的接口（只含 RecordOperation + PrepareMaintenance 等真正需要的方法）更干净。

## 四、效率评估

| 路径 | 评估 |
|---|---|
| 热路径 write_file | 盘写同步 + 元数据异步，够用。PrepareMaintenance 多一次 DB INSERT，崩溃安全 > 1ms 延迟，权衡正确 |
| Backfill | 游标分页 + ctx 可中断，合理。但持 updateMu 跑整轮会让 worker 排队，batch 不宜过大 |
| 检索路径 | Index.Query → uuids → 批量取件，不是 N+1，很好 |
