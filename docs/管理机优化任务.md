## 3. 管理机定位与依赖边界

`manager-go` 是单包文件生命周期库：负责文件内容、UUID 物理位置、逻辑目录、谱系、取件、恢复和盘库对账。

- **Manager**：协调文件与元数据，不依赖 HTTP、MCP 或具体数据库实现。
- **Store**：由调用方注入的元数据契约；SQL 和事务由 `mcp-server-go/internal/repo` 实现。
- **describer-go**：纯“字节 → 确定性事实”引擎，供 T2/T3 重分析使用。
- **core**：负责授权外的编排、耐久维护任务、属性/索引更新协调。
- **indexer**：进程内派生索引；Manager 不持有 indexer 实例，只通过 `IndexSink` 通知适配器。
- **common**：提供安全路径、盘读、校验和等纯工具。

当前仍保留 `IndexSink` 和 Manager 内的 T2/T3 分析写库路径。历史上“移除 Manager sink、统一所有属性提交、引入 revision/CAS”等属于后续设计，不是当前事实。

## 5. 已确认的当前行为与不变量

### 5.1 身份、路径和物理布局

- UUID 是文件身份；逻辑路径是元数据唯一键。
- 物理路径由 UUID 和逻辑路径扩展名派生，agent 不直接依赖随机物理文件名。
- 目录显示名称与逻辑键分离，允许同名文件。
- 路径必须经过安全校验，禁止目录穿越和非法名称。

### 5.2 新建与导入

当前流程：

1. 校验逻辑路径和来源。
2. `ReserveMeta` 原子占位并取得 UUID。
3. 写 `<uuid派生路径>.partial`。
4. 完整复制、`Sync`、关闭。
5. 使用排他硬链接发布正式文件。
6. `CompleteIntake` 确认完成。

关键约束：

- 管理机不再设置文件本体的统一大小上限；`Write`/`WriteBytes`/`Modify` 接受调用方已放入内存的内容，大文件应使用 `WriteReader`、`ImportFile`、`CopyByLogic` 或 `CopyInDirectory` 流式落盘。
- `describer.MaxFullBytes` 的 5 MiB 仅用于分析截断；取件缓存单条目上限也仍为 5 MiB。两者都不是文件大小上限。
- HTTP 大文件上传使用 `multipart/form-data`，MCP 大文件优先使用 `source_path`；JSON/Base64 会产生额外内存占用。
- 同逻辑键包括软删、幽灵和占位记录，均拒绝覆盖。
- 发布前失败会归档本次占位并释放原名称；发布后确认失败保留 pending，供启动恢复。
- 临时文件保留作证据，不把“普通文件存在”直接当作完整成功。
- 当前没有目录项 `fsync`，因此不声称断电耐久性已经验证。

### 5.3 修改与移动

- 修改使用 `.modify-*` 暂存，保留正式文件直到完整替换发布。
- 修改不再限制本次写入内容大小；追加后的最终文件大小也不受管理机上限约束。
- 同扩展名移动只改元数据逻辑键，UUID 和物理路径不变。
- 扩展名变化会先持久化 pending move，再排他发布新物理路径，最后确认。
- 修改、移动和打开阶段通过同一个 `mutation` 互斥锁协调；该保证仅限单实例。

### 5.4 复制

- `CopyInDirectory` 支持 UUID 目录复制，并在占位事务中固定目录关联和 `copied_from`；内容通过 `WriteReader` 流式复制。
- 普通 MCP `copy_file` 与 HTTP `/api/files/copy` 通过 `CopyByLogic` 流式复制内容；内容与元数据仍不是同一原子事务。

### 5.5 取件、缓存和下载

- `Locate`/`LocateMany` 返回位置；`Open`/`Read` 返回内容。
- 软删文件可追溯定位，但内容入口拒绝读取。
- pending intake/move 不进入可取件结果。
- `Open` 对不超过单条目缓存上限的文件使用 `os.ReadFile` 读入缓存；大文件旁路流式读取。
- `Read(limit)` 当前先调用 `Open`，再通过 `io.LimitReader` 截断；小文件仍可能先被完整读取和缓存。
- `StreamByLogic` 是下载专用流式入口，不走缓存。
- 下载票据绑定路径/UUID/有效期，但当前 HTTP 下载端点自行解析物理路径，并未统一使用 `StreamByLogic`。

### 5.6 目录、删除、恢复与清理

- 目录只存元数据；文件通过随机逻辑键加显示名称支持同名。
- 启动恢复顺序：`RecoverPendingMoves` → `RecoverPendingIntakes` → 索引重建 → 维护任务恢复。
- 移动恢复失败会中止启动；入库恢复失败当前只告警并继续。
- Manager 没有公开的主动删除/恢复软删除方法。主动删除由 `core.Delete` 更新 DB；T2 对连续 3 轮缺失文件执行幽灵软删。
- `PlanCleanup`/`ApplyCleanup` 只显式归档已发布且与正式文件同一 inode 的 `.partial`；未知孤儿、修改暂存和旧移动路径只报告。
- 清理归档不等于释放磁盘空间，也不支持多实例或外部程序同时改盘。

## 6. 候选优化方向（未排期）

以下是当前代码中可量化的改进点，不代表已经选择实现。

| 候选方向 | 当前证据 | 可能收益 | 必须先补的验证 |
|---|---|---|---|
| 真正的限读 | `fetch.go` 的 `Read` 先 `Open`，小文件经 `os.ReadFile` 入缓 | 降低大文件限读场景的 IO/内存 | `Read(limit)` 不同大小文件的读取字节、缓存占用和语义测试 |
| 复制元数据原子性 | 内容已流式复制，但 `CopyMetadata` 仍在内容发布后单独执行 | 减少内容已创建但谱系/属性未复制的窗口 | 复制中断、重名、权限、谱系与恢复测试 |
| 统一 T2/T3 属性提交路径 | `updater.go` 仍直接 `GetMeta/Merge/Upsert/sink.Update` | 收敛写入顺序，减少与 core 平行逻辑 | 并发 T1/T2/T3、迟到更新、删除胜出和重启恢复测试 |
| 启动恢复失败策略 | `main.go` 对 intake recovery 仅告警继续 | 避免带未收敛状态接收请求 | 恢复失败时 fail-fast 与可观测性需求确认 |
| 回填减少全量哈希 | `updater.go` 的快路径后仍对新鲜文件计算全文件 checksum | 降低大库 T2 扫描成本 | 新鲜度判定等价性、mtime/checksum 漂移和外部改文件测试 |
| Audit/LogicTree 流式化 | `audit.go`、`tree.go` 聚合全量行/文件 | 降低大库内存峰值 | 分页/游标一致性、取消、稳定排序和结果等价测试 |
| 目录创建并发协调 | `CreateDirectory` 未使用 `mutation` | 减少父路径竞态窗口 | 并发创建同名/父子目录与 DB 冲突测试 |
| 扩展名移动旧链接处理 | `finishStorageMove` 保留旧硬链接作恢复证据 | 减少重复目录项和潜在空间占用 | 恢复窗口、inode、审计和清理策略确认 |
| Manager 生命周期闭环 | 无公开 Delete/Restore | 明确软删/恢复归属 | 权限、维护任务、索引和物理保留策略 |
| 性能基线与 Fuzz | 当前 67 项测试，无 Benchmark/Fuzz | 用数据选择优化，发现边界输入 | 先建立可重复 benchmark 和路径/输入模糊测试 |

建议第一步先选择 1–2 个候选方向，补特征测试和基准，再决定实现；不要同时展开所有架构演进。

## 7. 优化约束与验收标准

### 7.1 必须保持的约束

- UUID 稳定；移动/改名后仍可按 UUID 取回正确对象。
- 同名不同 UUID 不串件。
- 正式文件不在未完整写入时可见；失败不误报成功。
- 重试不重复创建、不重复追加、不重放已完成的物理副作用。
- 路径校验、防穿越、软删/pending 拒绝读取语义不退化。
- 旧路径数据和旧物理布局仍可按 UUID 读取。
- Manager 不 import HTTP、MCP、repo 或 indexer 实现。
- 单实例保证不能包装成跨实例事务保证。
- 不做无关重构，不新增抽象除非有真实共享职责。

### 7.2 完成标准

- 选定方向有明确的 before/after 行为或性能证据。
- `manager-go` 单测、vet、race 全部通过。
- 受影响时运行 `mcp-server-go/core`、`internal/repo` 回归。
- 涉及数据库时使用独立测试库/临时表，绝不连接生产库。
- 公共接口变化必须同步调用方、测试和文档。
- 决策、验证结果和未完成项及时写回本文。
