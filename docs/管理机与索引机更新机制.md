# 管理机与索引机更新机制

> 2026-10-09。实施记录：修改/移动/软删除已接编排机维护门面；PostgreSQL 持久任务与认领恢复已接入；T2/T3 管理机索引通知经编排机适配器串行化。完整快照/revision 与所有写路径统一仍是后续批次。

## 当前落地范围

- MCP `modify_file`/兼容别名、`patch_file`、MCP/HTTP move 经过 core 门面；门面先持久化 UUID 任务，再调用 Manager，之后同步分析当前 DB 路径并更新索引。
- 软删除用同一耐久任务；重试读取当前行，已软删则卸载索引，仍有效则重分析。不会依据旧任务重放删除，避免旧意图影响后续有效状态。
- 每次维护独立记录任务，保留各操作的失败证据；`FOR UPDATE SKIP LOCKED` 原子认领 ready/到期 retry，prepared 只在启动恢复后处理。单实例由编排机锁协调文件操作与任务刷新，失败退避，累计三次失败后停止自动尝试。
- 管理机不直接持有 indexer；T2/T3 兼容回调由 core `ManagerIndexSink` 适配并串行进入统一索引 sink。
- 移动物理恢复继续由 `move_operations` 承担；恢复完成后周期维护任务读取当前 UUID 路径重分析。

仍未完成：新建/导入/复制的操作前 intent、属性 revision 快照接口、失败任务管理 API、管理机启动移动恢复后的即时任务生成、多实例 lease/CAS。

## 决策摘要

采用“管理机负责文件生命周期，编排机负责属性与索引”的单写者模型。

- 管理机只执行文件写入、修改、移动、复制、软删除等生命周期操作；返回含 UUID、当前逻辑键和变更类型的结果，不直接分析文件、不直接更新索引。
- 编排机是描述属性与索引的唯一协调者：读取当前已发布文件，分析并提交完整属性快照，再将该快照发布到索引。
- 文件维护后的通知使用持久化待处理记录，不只依赖内存事件队列。工作进程按 UUID 重读最新状态，合并同一 UUID 的待处理任务；重放必须幂等。
- 索引操作从 `Update(uuid, old, new)` 逐步收敛为 `Replace(uuid, revision, attrs)` 和 `Remove(uuid, revision)`。索引按自身旧快照替换，并拒绝旧 revision。
- 启动先恢复管理机未完成的文件操作，再重建索引，再启动维护任务与接收请求。重建成功后消费未完成记录；任何失败保留可重试状态。

这样仍然只有 DB 属性是事实源，索引可以随时从 DB 重建；持久化记录只负责确保文件改动后的属性分析不会因进程崩溃而永久漏掉。

## 当前重复职责

启动装配由编排机提供 `ManagerIndexSink` 适配器；Manager 不持有索引实例。MCP 修改/patch/移动经编排机门面，T2/T3 更新则由该适配器串行进入编排机索引写入点。旧的管理机内重分析实现只保存在 `旧内容/2026-10-09/manager-go/`。

问题的核心不是接口能否直接调用，而是**谁拥有一次属性变更的完整生命周期**。让 Manager 同时改文件、分析、落属性、喂索引，会把管理机变成第二个编排器，并使 MCP/API/回填各自出现不同的更新顺序。

## 唯一处理链

```text
调用方
  │
  ▼
编排机维护门面
  ├─ 创建持久化任务 intent（按 UUID）
  ├─ 调用管理机执行文件操作
  ├─ 管理机返回 MutationReceipt（uuid/path/kind）
  ├─ 将任务标记 ready
  └─ 唤醒维护 worker（唤醒可丢，任务记录不可丢）
         │
         ▼
worker 按 UUID 串行、合并重复任务
  ├─ 读当前 DB 行和当前逻辑键
  ├─ 检查软删/pending/文件已发布状态
  ├─ 从当前文件重分析
  ├─ DB 提交完整属性快照及递增 revision
  ├─ Index.Replace(uuid, revision, snapshot)
  └─ 标记任务完成
```

查询仍由索引返回 UUID 候选，随后从 DB 取件并复判软删、发布状态和权限。索引不获得文件路径/权限决策，也不做磁盘 IO。

## 持久化任务与故障恢复

增加小型 `metadata_maintenance_jobs`（命名可调整）记录：`job_id`、`uuid`、`kind`、`status`、`created_at`、`updated_at`、`attempts`、`last_error`。`status` 至少有 `prepared`、`ready`、`done`、`cancelled`。

1. 操作开始前写 `prepared`。唯一未完成约束按 UUID 合并/串行，不重复堆同一 UUID 的重分析任务。
2. 文件操作成功后写 `ready`。worker 只消费 ready。
3. worker 永远凭 UUID 读最新元数据和逻辑键，不相信任务中可能过时的路径；一次成功分析覆盖任务创建时的中间状态。
4. DB 属性事务成功后再更新内存索引，再将任务标记 done。索引更新是幂等替换；若进程在 DB 提交后崩溃，重试从 DB 读快照并再次 Replace。
5. worker 失败保留 ready 与最后错误，退避重试；不得把失败当完成。提供只读失败计数和手动重试入口，先不加复杂定时调度 UI。
6. 启动时 `prepared` 需结合管理机已有的 intake/move 恢复记录复判：若相关文件操作已完成，则晋升 ready；若已明确失败则 cancelled。无法判定时保留并告警，不能静默丢任务。

管理机已有 `move_operations`/`intake_operations` 应优先复用其文件发布状态，不另造一套物理恢复协议。属性维护 job 只管“何时重分析并更新索引”。对普通 overwrite/append，若崩溃留下 prepared，重分析当前文件是安全的；对尚未发布的 `.modify-*` 不分析暂存内容。

## 操作语义

|操作|文件层结果|属性/索引动作|
|---|---|---|
|新写入、外部导入|发布正式文件并确认 intake|成功后建立/完成 UUID 维护任务；初次属性由统一 worker 分析，替代独立的重复描述事件|
|复制|复制源内容到新 UUID|目标 UUID 独立分析；不能把源 UUID 的桶挂载复制过去|
|覆盖、追加、patch|原子发布正式文件|ready 后按 UUID 重新分析当前文件；重放不再追加内容，只重分析|
|移动、改名|DB 逻辑键和 move 恢复状态提交，完成物理发布|UUID 不变但分析名可能变化，必须重新分析名称相关属性；worker 读当前路径|
|软删除|DB 标记删除|成功后 `Index.Remove(uuid, revision)`；未完成的旧分析任务不得复活该 UUID|
|恢复软删除|DB 明确恢复发布状态|重新分析当前文件并 Replace；不可简单恢复旧桶快照|
|下载、读取、`.partial` 证据归档|不改变被索引内容/属性|不触发索引更新|
|后台回填、手动分析|当前已有分析入口|改为调用同一个属性提交与索引发布函数，不保留平行实现|

T1/describe 等没有物理维护操作的属性写入也必须复用同一个 `commitAttributesAndIndex`：先提交 DB，再以数据库接受的完整快照和 revision 更新索引。这样文件事件和人工标注不会各自定义索引更新方式。

## 并发与顺序

- worker 按 UUID 单飞；同 UUID 新任务可合并为“重新读取最新状态”，无需逐条重放每次内容中间态。
- `revision` 是 DB 中专用的属性/生命周期递增版本，不用 `updated_at`（下载也会更新）或描述算法 `ver` 代替。
- 索引只接受 revision 不小于当前版本的快照。Remove 也记录 revision，防止迟到的旧 Replace 复活已删除文件。
- DB 属性读改写在同一事务或 CAS revision 下完成，防止 T1 与 T3 同时保留各自旧快照导致彼此覆盖。
- Manager 的 `mutation` 锁仍保护单实例物理修改，不作为跨进程一致性机制。
- 先保持单个服务实例。若未来多实例，必须改用 DB job claim/lease 与 revision CAS，不能依赖 Go channel 或本地 mutex。

## 接口调整建议

- 从 `manager.New(..., sink, ...)` 移除 `IndexSink`，避免管理机直接依赖索引；Manager 返回 `MutationReceipt{UUID, Path, Kind}`。对于目录移动等已返回 receipt 的路径扩展同一契约。
- 在编排机提供 `ModifyFile`、`MoveFile`、`ImportFile`、`DeleteFile` 等维护门面；所有 API/MCP 工具调用这些门面，不再自行 `Manager.Modify` 后另发 `KindModify`。
- 持久任务表由 repo 实现 claim/complete/retry，job worker 与 HTTP/MCP 请求均调用同一执行函数。
- 把 T1、describe、T2/T3 最终写索引收敛到编排机一个 `commitAttributesAndIndex`；管理机不再独立 sink。
- 索引接口换成基于快照和 revision 的 Replace/Remove。迁移期间可用适配器包装旧 Update，但适配器内部必须维护真实旧快照，不能信任任意调用者提供的 old。

## 分批实施

### 第 1 批：收回重复分析

撤销最近加到 `manager-go` 的 `syncMaintainedFile` 自动重分析和对应移动恢复钩子；保留 Manager 的物理操作与 receipt。把 HTTP/MCP 修改和移动入口统一走编排机门面，验证修改只分析一次、移动刷新名称属性。此批先不改索引数据结构。

### 第 2 批：单一提交函数与幂等快照

增加 `commitAttributesAndIndex`，所有写路径使用 DB 提交后的完整属性快照；indexer 增加 Replace/Remove 并保存快照。补增量更新与重建同结果、软删后迟到更新不复活、输入 map 改动不影响索引的测试。

### 第 3 批：持久任务

先覆盖 overwrite/append/move 这些管理操作：prepared → ready → worker → done，增加故障注入覆盖“文件已发布、任务未 ready”“DB 已提交、索引未更新”“worker 重启”。再迁移新建、导入、复制和删除，避免一次变更横跨所有入口。

### 第 4 批：统一所有触发器

将 T1、describe、T2/T3、恢复软删接入同一提交/发布 API；移除旧 `Sink.Update(old,new)` 接线和重复事件；文档记录操作矩阵及故障重试方法。

## 验收标准

1. 任何正式文件内容或分析名改变，最终都对应当前 UUID 的最新 DB 属性快照和索引 revision。
2. 同一维护任务重复执行不改变文件内容，不产生重复索引挂载。
3. 强制在文件发布、DB 提交、索引更新三个边界杀进程，重启后任务可恢复；DB 仍是重建索引的唯一来源。
4. 修改工具和 HTTP/MCP 路径不重复分析；move/rename 后按旧名称查不到、按新名称能查到。
5. 软删除任务与迟到分析交错时，删除状态胜出；pending intake/move 不被查询或索引成已发布状态。
6. 故障有 UUID、操作类型、逻辑键、尝试次数和错误记录；可定位并显式重试。
